## 1. 需求与边界

### 1.1 一句话

以「期」为单位的**站方编辑专栏**：每期一个主题 + 前言 + 一组插件，每个插件带简述、推荐理由、评分（待设计）与详情链接，用于对外呈现「精选插件」。

### 1.1.1 入选前提：被推荐的插件必须已有官方测评

> 使用者 2026-11-09 裁定：
> **精选是站方选的，也必须由官方给出测评。被选进精选的插件，一定已经有一篇官方测评。**

理由：精选是站方的**背书**。如果推荐一个官方自己都没测过的插件，那只是转发；
有官方测评在前，读者点进精选就能读到站方对这个插件的正式结论，背书才成立。

#### ⚠️ 实现现状：这条规则**尚未在代码里执行**（TODO-精选官方测评前置校验）

实查 `src/server/modules/featured/index.ts` 的 `validateItem`（约 189-194 行），
它只校验「插件存在」：

```ts
const plugin = db.prepare('SELECT id FROM plugins WHERE id = ?').get(input.pluginId);
if (!plugin) throw err.input('所选插件不存在。', [...]);
```

**没有校验该插件是否有 `source_kind='site'` 且已发布的测评。**
也就是说现在管理员可以把一个没有官方测评的插件选进精选，代码不会拦。

#### 待补的校验

在 `validateItem` 的插件存在性校验之后加一段：

```sql
SELECT 1 FROM reviews r
  JOIN content_entities ce ON ce.id = r.id
 WHERE r.plugin_id = ?

   AND r.published_revision_id IS NOT NULL

```

查不到就报「这个插件还没有官方测评，暂不能进精选」。

**注意**：这条校验要放在**保存条目**时（`validateItem`），不要只在发布时查——
否则草稿期能选、发布时才报错，管理员要回头改一遍清单。

有的话要么补测评，要么给历史条目留一条豁免（按 `created_at` 早于上线日期判断）。

| # | 决策 | 说明 |

## 3. 数据模型（迁移 0033）

### 3.1 `featured_columns`（一期一行）

| 字段 | 类型 | 约束 / 说明 |
|---|---|---|
| `id` | TEXT PK | UUIDv7 |
| `issue_number` | INTEGER | `> 0`，**UNIQUE**；创建时取 `MAX+1`（同事务） |
| `title` | TEXT | 1–80 字，`trim <> ''` |
| `theme` | TEXT | 1–200 字，本期主题句 |
| `preface_md` | TEXT | ≤ 20,000 字，Markdown 原文（渲染时统一净化） |
| `status` | TEXT | `draft` / `published`，默认 `draft` |
| `published_at` | INTEGER NULL | `CHECK ((status = 'published') = (published_at IS NOT NULL))` |
| `created_by` | TEXT | → `users(id)`，RESTRICT |
| `request_key` | TEXT | 新建去重；`UNIQUE(created_by, request_key)`，重复点「创建」不会多出一期 |
| `state_version` | INTEGER | 乐观并发，默认 0 |
| `created_at` / `updated_at` | INTEGER | ≥ 0 |

索引：`UNIQUE(issue_number)`、`UNIQUE(created_by, request_key)`、`IDX(status, published_at DESC, id)`。

### 3.2 `featured_column_items`（一个插件一行）

| 字段 | 类型 | 约束 / 说明 |
|---|---|---|
| `id` | TEXT PK | UUIDv7 |
| `column_id` | TEXT | → `featured_columns(id)` **CASCADE** |
| `plugin_id` | TEXT | → `plugins(id)` RESTRICT（插件被删时不许静默丢推荐） |
| `position` | INTEGER | ≥ 0，**应用层规范化为 0..n-1** |
| `summary` | TEXT | 1–200 字，插件简述 |
| `reason` | TEXT | 1–1000 字，推荐理由 |
| `score` | INTEGER | **NOT NULL**，`CHECK (score BETWEEN 0 AND 100)`，百分制整数 |
| `detail_url` | TEXT NULL | 官方测试集链接；只接受 `https://`，≤ 2000 字；站内域名由渲染层判断 |
| `recommended_version` | TEXT NULL | 展示用（如 `1.2.3`），不参与逻辑 |
| `created_at` / `updated_at` | INTEGER | ≥ 0 |

约束与索引：

- `UNIQUE(column_id, plugin_id)`：同一期不重复推荐同一插件；
- **不建** `UNIQUE(column_id, position)`：重排过程中会出现中间态冲突（SQLite 不支持延迟约束），顺序由应用层整体重写保证；
- `detail_url` 仅校验协议与长度（是否站内由**渲染**判断，不在库里固化域名，换域名不返工）；
- `IDX(column_id, position, id)`，`IDX(plugin_id)`（供「精选」标签反查）。

### 3.3 `featured_subscriptions`（订阅栏目）与通知扩展（迁移 0034）

| 表/字段 | 说明 |
|---|---|
| `featured_subscriptions(user_id PK, created_at)` | 每人一行 = 订阅「精选」栏目；没有"订阅某一期"的形态 |
| `notifications.kind` 增 `featured_published` | 新期发布通知；CHECK 一并放开「非评论类可无 comment_id」「栏目类可无 content_entity_id」 |
| `notifications.link_url` | 栏目类通知没有 content_entity_id，跳转地址（`/featured/N`）存在这里 |

投递：发布事务内对**所有订阅者**各投一条，去重键 `featured:{期号}:{收件人}`；触发者是固定 id 的系统账号。

### 3.4 为什么分两张表 + 不做快照

- 分两张表：一期是「元信息 + 有序清单」，清单条目有独立生命周期（增删、改文案、换位），塞进 JSON 会让排序与约束都变难；
- **不做发布快照**：专栏是编辑内容，不是用户投稿；发布后允许改文案（D5），读者看到的就是最新编辑稿。代价是「历史期不可复原」，已在 §9.4 记为已知取舍。

## 4. 状态机与权限

### 4.1 状态机

```
[新建] → draft ──publish──→ published
                ←─（不提供下架；确需下架时另议 archived）
```

| 动作 | 允许的状态 | 说明 |
|---|---|---|
| 新建 | — | 自动取下一期号，`status=draft` |
| 编辑元信息 / 清单 | draft、published | published 编辑后 `updated_at` 变化，读者页显示「最后更新」 |
| 发布 | draft | 置 `published_at`；发布前校验：标题/主题/前言非空、至少 1 个插件、每项简述与理由非空 |
| 删除 | draft 仅 | 物理删除（CASCADE 条目）；已发布期不可删 |

### 4.2 权限矩阵

| 能力 | 匿名 | 登录用户 | 管理员 |
|---|---|---|---|
| 浏览已发布期 | ✅ | ✅ | ✅ |
| 浏览草稿 | ❌ | ❌ | ✅ |
| 创建 / 编辑 / 发布 / 删除草稿 | ❌ | ❌ | ✅ |
| 「创建精选专栏」按钮可见 | ❌ | ❌ | ✅ |

### 5.1 读端（公开）

### 5.2 管理端（仅 admin）

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/admin/featured?status=all` | 管理列表（含草稿） |
| POST | `/api/admin/featured` | 新建草稿：`{ title, theme, prefaceMd, requestKey }` |
| GET | `/api/admin/featured/{issue}` | 编辑页数据（含条目与当前 `stateVersion`） |
| PATCH | `/api/admin/featured/{issue}` | 保存元信息 + **整份清单**（顺序与逐项文案一起提交，`expectedVersion` 乐观锁） |
| POST | `/api/admin/featured/{issue}/publish` | 发布（同样带 `expectedVersion`） |
| DELETE | `/api/admin/featured/{issue}` | 删除草稿 |

**为什么清单整份提交**：换位与文案编辑必须原子落库，逐条 PATCH 会出现「顺序已变、文案没变」的中间态；整份提交 + `stateVersion` 把并发冲突变成一次明确的 409。

### 5.3 编辑页的两个「选插件」来源

| 来源 | 复用接口 |
|---|---|
| 我的收藏夹 | `GET /api/me/favorites`（已有，返回收藏夹与夹内插件） |

## 9. 开放问题（待设计 / 待确认）

### 9.1 评分（已定案：编辑功能性评分，百分制）

**规则**

- **谁给**：编辑（管理员）人工填写，按「插件功能性」判断；
- **量纲**：百分制整数 `0–100`，必填，**不给半步/小数**（避免「87.5 比 87 好」这种无意义精度）；
- **不聚合**：不由站内评测、档位或票数推导；读者看到的分数就是编辑当期给出的判断；
- **随期**：同一插件在不同期可以给不同分（插件在演进，推荐语境也不同）；

**界面与文案（必须同时出现，不能只显示数字）**

- 展示形如 `评分 87/100`，并在同一行标注 `编辑评分` ；
- 期详情页底部固定一句：`评分为编辑依据插件功能性给出的主观判断，不代表官方认证。`

**为什么不做读者评分**：站内已有「有帮助」票与测评档位，再叠一层读者打分会有两套互相打架的
「受欢迎程度」；且读者评分需要防刷，属于独立课题。

### 9.2 官方测试集链接（已定案：每期手填）

- 每个插件条目可填**一条**链接，编辑在当期手填（不是评测的固定属性）；
- 只接受 `https://`；站内域名（同站路径/同 host）按站内链接处理——同窗口、可被搜索收录；
  其余按外链处理——新窗口 + `rel="nofollow noreferrer noopener"` + 「外部链接」图标；
- 站点域名不在库里固化（从请求头/配置推导），换域名不需要回填数据；
- 链接失效由编辑在下一期修正；本期不做自动探活（避免又一条外部依赖）。
