# PR：新用户教程（普通用户与访客）

分支 `feat/guide` → `main`。改动量：7 个文件，+903 / -1。

---

## 先说结论

站点此前**没有任何教程或引导**。新用户第一次打开会面对六个并列的主导航（插件 / 整合包 / 评测 / 精选 / 讨论区 / 规范），
三类内容之间的关系、哪些功能要登录、投稿从哪进，全靠猜。

本 PR 补上教程：**一份完整文档 + 一个站内页**，覆盖访客与普通用户（含投稿能力）。

教程要解决的不是「按钮在哪」，而是**「第二次访问还不来」**——访客不知道登录能得到什么就不登录；
注册了的人不知道能投稿，就永远只是读者。

### 入口：主导航的「教程」

排在「规范」之后——两者都是说明性内容，语义相邻。

这一条在开发中改过两次，过程值得记一笔：

1. 原设计写「放页脚」，实施时发现**站点根本没有页脚组件**；
2. 一度改放两个账户菜单（登录菜单 + 账户菜单），但**藏在下拉菜单里更不容易找到**——
   新人恰恰是「不知道该点哪里」的那群人，收进菜单等于没放；
3. 最终放主导航。导航从六项变七项，这是可接受的代价：**入口的可发现性比排列紧凑更重要**。

## 文档的 12 节

按「读者此刻想干什么」组织，不按功能树罗列。

| # | 章节 | 要回答的问题 |
|---|---|---|
| 1 | 这是什么站 | 三类内容的关系（插件是被测对象、评测是结论、整合包是推荐组合） |
| 2 | 不登录能做什么 🔓 | 访客能看的全部内容 |
| 3 | 登录与变化 | 凭什么要登录；一张前后对照表 |
| 4 | 找插件 | 目录搜索筛选、详情页各块的含义 |
| 5 | **读评测（重点）** | 为什么没有星级、五状态结论、什么是证据链 |
| 6 | 整合包 | 与插件的区别、安装命令 |
| 7 | 精选专栏 | 与官方测评的关系 |
| 8 | 讨论区 | 主干：分区、发帖、两层回复、草稿、举报 |
| 9 | 收藏与个人中心 | 三类收藏独立、删夹会移回默认夹 |
| 10 | 我想投稿 | 四条投稿路径各自怎么走 |
| 11 | **遇到问题该找谁（重点）** | 举报 / 纠错 / 问题反馈三条通道的分工 |
| 12 | 常见问题 | 12 条真实会问到的 |

## 三处特意用力的地方

### 1. 全文标注 🔓 / 🔐

访客最想知道的就一句话：**我现在不注册能不能用**。逐个功能标，比在开头笼统说一句有用得多。

### 2. 第 5 节单独讲「这里没有星级」

本站不给总分、不用星级，结论只能五选一：真有用 / 帮倒忙 / 没啥差别 / 还说不准 / 没法测，
其中前三个**必须附证据链**（至少一条能点开的链接）。这是本站区别于普通博客的核心，教程里讲了含义也讲了为什么。

### 3. 第 11 节把三条通道做成对照表

| 通道 | 管什么 | 不管什么 |
|---|---|---|
| 举报 | 内容违规（垃圾广告、辱骂、错误信息、版权） | **不处理**资料写错 |
| 反馈资料错误 | 只改两项：**展示名**、**简介** | 分类错误、评测内容 |
| 问题反馈 | 站点本身的问题（功能异常、账号、建议） | 某篇内容的对错 |

新用户最常在这里用错，用错的表现是**白等很久**。所以单独一节 + 一张「三句话记住怎么选」。

## 写作原则

| 原则 | 做法 |
|---|---|
| 先讲能做什么，再讲怎么点 | 每章开头一句话说明能帮读者达成什么 |
| 不写「点击这里」 | 写「顶部导航的『插件』」而不是「左边第三个按钮」——位置会变，语义不会 |
| 失败路径要写 | 每章至少一条：提交被拒怎么办、帖子为什么审核中、收藏为什么找不到 |
| 不承诺时长 | 不写「审核 24 小时内完成」，写「审核通过前内容不会公开」 |
| 遵守用词规范 | 按 `docs/用词规范.md` 处理，「证据链」在标题与表格保留术语并就地下定义，正文用「能点开的记录」——与 `/spec` 页同一处理方式 |

**本版不附截图**（使用者裁定：附截图会显得臃肿）。页面结构用表格逐块说明，位置用语义描述。

## 事实核对

教程里的数字与位置**全部实查**过，不是凭印象写的：

## ⚠️ 附带一条待办：精选的入选前提尚未在代码里实现

使用者 2026-11-09 裁定：**被选进精选的插件，一定已经有官方测评**。精选是站方的背书，
推荐一个官方自己都没测过的插件那只是转发。

**这条规则此前设计文档没写、代码也没做。** 本 PR 只补了文档（`设计-精选专栏.md` 新增 §1.1.1）：

- 写清了规则与理由；
- 写明实现现状：实查 `featured/index.ts` 的 `validateItem` 只校验「插件存在」，**不校验是否有已发布的官方测评**；
- 给出了待补的校验 SQL 与两条实施注意（校验要放在保存条目时、历史条目要盘点灰度）；
- 用 `TODO-精选官方测评前置校验` 标记，可搜索定位。

使用者裁定「先不补，但标记出来」，所以**本 PR 不含这段代码**。补的时候要连带做三件事：
① `validateItem` 加校验；② 补测试（无官方测评的插件被拒）；③ 盘点线上历史精选条目是否需要豁免。
